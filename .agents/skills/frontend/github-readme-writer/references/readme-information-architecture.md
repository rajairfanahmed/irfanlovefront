# README Information Architecture

A README should help a new reader answer, in order: What is this project? Is it relevant to me? What does it do? How do I run it? How is it organized? How can I contribute or get help?

## Recommended structure

1. Project name and accurate one-line description.
2. A real screenshot, short demo, or architecture visual when it adds value.
3. What the project does and who it serves.
4. Implemented features, separated from planned work.
5. Technology and architecture overview, based on actual dependencies and code.
6. Prerequisites and exact setup steps.
7. Environment configuration with safe example names and no secret values.
8. Development, lint, test, type-check, build, and deployment commands that exist.
9. Project structure or contribution guidance where useful.
10. License, security, support, and contribution details only when verified.

## Match the project size

A small library may need installation, usage, API examples, and compatibility. A full-stack application may need architecture, local setup, environment configuration, and test instructions. Do not add empty sections to imitate a large open-source project.

## Navigation

Use a short contents list for long documents. Keep headings predictable and links valid. Avoid repeated introductions and slogans that add no information.
